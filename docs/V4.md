# V4 — Strava Integration

## Goal

Add user accounts and a read-only Strava connection while preserving V1 manual logging, V2 Gemini, and V3 Supabase activity storage.

## Features

- Supabase email/password sign-up, login, logout, current user, and protected dashboard
- User-owned running activities with per-user Row Level Security
- Server-side Strava OAuth and account connection
- Read-only activity sync and run-only filtering
- Strava activity normalization to the existing kilometer/seconds-per-kilometer model
- Duplicate prevention using `(user_id, source, external_id)`
- Encrypted Strava token storage, refresh, and disconnect/revocation
- Manual and Strava activities in the same history and statistics
- Existing Gemini recommendation and rule-based fallback

## Architecture

```text
User → Supabase Auth → protected Next.js app
                         ├─ manual activity → user-scoped Supabase row
                         ├─ Strava OAuth/API → normalize → user-scoped Supabase row
                         └─ database history → Gemini → recommendation/fallback
```

OAuth callback, token exchange/refresh, sync, and disconnect all happen in server routes. The browser receives only connection status and sync counts, never tokens.

## Security

- Activity routes verify the Supabase user, set `user_id` server-side, and use RLS policies keyed to `auth.uid()`.
- Strava requests use only the `activity:read_all` scope. No write scope is requested.
- OAuth `state` is stored in a short-lived HttpOnly, SameSite=Lax cookie and checked on callback.
- Access and refresh tokens are encrypted with AES-256-GCM using `STRAVA_TOKEN_ENCRYPTION_KEY` before they are stored.
- A service-role client is used only on the server for the Strava token table, after verifying the user. It is never exposed to browser code.
- The Gemini endpoint queries the current user's Supabase rows instead of trusting activity data supplied by the browser.

## Data migration

The V3 schema has shared rows without an owner. V4 adds nullable `user_id` so existing data is preserved while RLS is enabled. Create the intended first account, then use its Supabase Auth UUID to backfill the old V3 rows and make `user_id` required, following [Database](./DATABASE.md). Do not assign old shared rows if they should not belong to that account.

V2 browser activities still use an explicit import prompt. The user's original activity IDs are stored as unique legacy IDs for that user; the old browser copy is removed only after the server verifies the import.

## Limitations

- No social login, social features, Strava posting/editing, or advanced analytics.
- One Strava connection is supported per Supabase account.
- Sync imports running, trail-running, and virtual-running activity types only.
- OAuth and live Strava/Gemini requests require configured developer applications and credentials.
- Full existing V3 data ownership requires the documented manual UUID backfill.
- Supabase email confirmation and allowed redirect URLs must be configured in the Supabase dashboard.

## Testing checklist

- Sign up, confirm email if enabled, log in, and log out.
- Confirm an unauthenticated browser is sent to login and user A cannot see user B's activity rows.
- Add a manual run and confirm it has `source = manual` and the current `user_id`.
- Connect Strava, verify status, sync twice, and confirm the second sync creates no duplicate rows.
- Confirm non-running activities are ignored and distance/date/duration/pace are normalized correctly.
- Refresh an expired token and verify a revoked token asks the user to reconnect.
- Disconnect Strava; confirm the token record is removed and imported history remains.
- Test cancellation, invalid OAuth state, API/database failure, Gemini failure, and rule fallback.
- Check desktop, tablet, and mobile layouts.

Live account isolation, Strava OAuth, token refresh, sync, and revocation must be tested with the user's configured Supabase and Strava applications.
