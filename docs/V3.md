# V3 — Persistent Database

## Goal

Move running activity persistence from browser `localStorage` to Supabase. The database becomes the source of truth for the activity history, statistics, and AI training context.

## New features

- Supabase database storage for running activities
- Server-side create, read, and delete operations
- Database-backed statistics and recommendations
- Loading and database error states
- Explicit migration flow for V2 browser data
- Idempotent migration using a unique `legacy_id` value
- V2 Gemini recommendation and rule-based fallback preserved

## Architecture

```text
Next.js dashboard
      ↓
Server route handlers
      ↓
Supabase running_activities
      ↓
Statistics and training context
      ↓
Gemini API (on request)
      ↓
AI recommendation or V1 rule fallback
```

The dashboard reads activities through `GET /api/activities`, creates them through `POST /api/activities`, deletes them through `DELETE /api/activities/[id]`, and sends a compact database-derived context to the existing Gemini endpoint.

## Migration

On startup, the browser checks for V2's `runningActivities` key. If valid entries exist, the user can import them or choose “Not now.” Import uses the old activity IDs as unique `legacy_id` values, so a retry does not create duplicate records. The server verifies that all source IDs exist in Supabase. The browser removes the old activity key only after import verification and a successful database refresh.

## Limitations

- There is no authentication or user isolation. All users of the configured project share one table.
- The app is intended for local development and portfolio demonstration, not for storing personal data in a public deployment.
- Runner profile preference remains in browser `localStorage`.
- Gemini requires a valid API key; the rule-based recommendation still works without it.
